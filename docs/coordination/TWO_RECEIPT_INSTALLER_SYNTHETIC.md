# Synthetic two-receipt installer preflight

`scripts/two_receipt_installer.py` is a synthetic-only API, not connected to NSIS/batch/workflows. Existing APP and FULL receipt schemas are unchanged. A separately approved profile pins both receipt SHA256s, fake-script SHA256, Semver version and matching 40-hex app/full source commits. APP receipt has no source pin: `appSourceCommit` is an external attestation, not independently reconstructed Git provenance.

Metadata files are validated against reparse/path escapes then Windows-read-locked before parsing. FULL inputs use their existing held-handle hash verification. Every APP file is inventory-matched, locked and hashed; package version and policy bytes must match. Fixed destination bindings map launcher/icon/HTML/four locales/Node; other declared roles are compile-only. Duplicate payload bindings are rejected; the resulting target snapshot is a read-only mapping. All locks remain held across the synchronous Python fake process and release on success/failure. Existing input bytes are retained. No output file, compiler arguments, signing or real installer is generated.

The fake script is explicitly caller-approved/pinned executable code. This does not sandbox it. Tests demonstrate ordinary concurrent filesystem write/delete/rename denial, not malicious administrator resistance, explicit forced-parent-kill test or full SDK closure. Profile/source approval trust is external; this prototype does not establish public-policy validity, signatures, real NSIS target semantics or complete installer readiness. `installerReady` is always false.

Verification: `C:\Python314\python.exe -B scripts/test_two_receipt_installer.py -v` (seventeen joint-contract tests plus seven existing FULL tests). Node wrapper: from app, `..\runtime\node\node.exe node_modules/jest/bin/jest.js --runInBand test/two-receipt-installer.test.js`.


Adversarial follow-up: target component-prefix validation rejects file/ancestor collisions in either insertion order, case-insensitively. APP paths are checked from the captured canonical stage/app root while Windows Read-only-share file handles are held; each opened final handle path must match its expected canonical relative path. Root/component reparse and complete inventory checks repeat immediately before the fake child. A deterministic real Windows junction exchange before APP handle acquisition is rejected without child execution, redirected files remain byte-identical, and handles are released. A second boundary fixture inserts a late member immediately before final revalidation and is rejected. These checks still do not claim complete SDK closure, sandboxing or resilience to forced parent termination.


Child containment follow-up: `synthetic_child_job.py` starts Python with CREATE_SUSPENDED and no inherited handles, sets JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE, assigns the child before ResumeThread, then waits at most 3000ms. Assignment/configuration failure never resumes the child. On normal end, nonzero exit or timeout, the whole job is explicitly terminated and queried until active process count is zero (bounded cleanup wait); job/process/thread handles close in finally. APP/FULL input contexts surround this operation and release only afterwards. Windows tests verify surviving descendants are killed after success, exitcode error and timeout; input bytes are preserved and handles writable afterwards. Kill-on-close also protects job closure on owning-process exit, but explicit forced-parent termination and a real nested-job environment remains untested. No real compiler, toolchain or workflow integration.


Failure injection: five Windows fixtures fail exactly CreateJobObjectW, AssignProcessToJobObject, ResumeThread, TerminateJobObject or QueryInformationJobObject while all other calls use real APIs and real suspended Python processes. Every successfully created JOB/PROCESS/THREAD handle is closed once; pre-assignment failures never call ResumeThread, and failed resume never executes fake code. Cleanup failures rely on configured kill-on-close; spawned descendants are verified exited. All metadata, every FULL source and every APP file remain byte-identical and writable after return. Assignment denial models the fail-closed result of unsupported nested-job restrictions but does not prove support for arbitrary host job policies. Non-Windows mode fails closed; no real compiler is supported by this API.
