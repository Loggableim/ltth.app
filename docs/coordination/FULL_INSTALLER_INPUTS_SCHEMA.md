This separate contract does not modify or replace the APP_RUNTIME receipt and is not wired into the batch/compiler/signing path. `scripts/full_installer_inputs.py` validates an explicit declared inventory; successful verification always returns `installerReady:false`. Compiler-resolved SDK closure and actual toolchain identity remain unproven.

Top-level exact fields: name=`FULL_INSTALLER_INPUTS`, schemaVersion=1, sourceCommit=40 lowercase hex, toolchain={nsisVersion,pythonVersion,nodeVersion,windowsTarget} (explicit labels), closure=`declared-not-compiler-resolved`, inputs=[...]. Each input has exact fields name/role/root/path/bytes/sha256. SHA256 is 64 lowercase hex, bytes 0..128 MiB. Roots are trusted absolute directory bindings supplied independently by the caller, not arbitrary path strings selected by the manifest. Every payload, locale, Node member, script, macro/include/UI/language/plugin/stub/config resource must have its own explicit entry. No directory entries or wildcard expansion.

Required categories: launcher, icon, header/sidebar/splash BMP, license, launcher HTML, EN/DE/ES/FR locale, Node runtime, NSIS script, batch script, stage helper, Runtime builder, policy, Python runtime, SDK compiler/includes/resources/plugins, signing helper and signing tool. Categories are presence gates, NOT proof that every transitive SDK dependency has been declared. Actual full SDK closure requires an independently reviewed SDK manifest or separately authorized preprocessor evidence. Toolchain labels are assertions; this fixture verifier does not execute binaries to establish their versions.

`full-installer-inputs.synthetic.json` contains only synthetic names/bytes/hashes matching generated fixture payloads. Its aaaa sourceCommit and toolchain labels are placeholders, not an approved repository/toolchain pin. It is never usable as an official release inventory.

Before any hash: reject reparse points in trusted-root ancestors, root and every path component; reject traversal/absolute paths/control characters/wildcards, duplicate names/paths and missing categories. Resolve strictly within root. Windows CreateFileW opens GENERIC_READ with FILE_SHARE_READ only. After locking, GetFinalPathNameByHandleW must match the validated path; SHA256 and byte length are calculated using ReadFile on the held HANDLE itself. This prevents path reopen substitution from being mistaken for hashing the locked object. All handles remain open during the caller's context and close on validation failure/body exception/normal exit. The API itself starts no compiler or signer.

Boundary: trusted approved root bindings and approved manifest provenance are caller obligations. Ordinary writes/deletes/renames to locked objects are blocked; no global protection against malicious admin/kernel, altered verifier/runtime, forced process termination, directory mutation outside this inventory, dishonest manifest approval or incomplete SDK closure. Future compile integration must preserve this context for the child's entire lifetime and explicitly use this inventory instead of live wildcard trees. Signing outputs need a separate unsigned/signed byte attestation; certificate/timestamp binding and human SimplySign login/OTP are outside this verifier. No user data is removed, and no files are rewritten by verification.

Synthetic checks only: Python seven tests and Node wrapper; concurrency uses a Python fake process attempting ordinary file writes/deletes/rename. No real launcher/SDK binaries, credentials, compiler, installer, SimplySign, workflow or release inspected/executed.
